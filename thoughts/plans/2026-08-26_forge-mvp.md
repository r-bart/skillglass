**Status**: In Progress
**Source mode**: `devtronic:create-plan --from-spec`
**Source contracts**: `thoughts/PRODUCT.md`, `thoughts/DOMAIN.md`, `thoughts/ADAPTERS.md`, `thoughts/OPERATIONS.md`

## Overview

Build Forge as an open-source, local-first Electron desktop application for macOS, Windows, and Linux. The first complete vertical slice discovers installed skills, explains their evidence and effective scope, and then adds safe installation and update workflows limited to approved user-writable roots.

Forge does not activate, deactivate, uninstall, relocate, or otherwise configure skills in a harness. The filesystem remains authoritative; SQLite is a disposable projection plus a persistent snapshot and operation journal.

## Planning Baseline

- The repository is greenfield: there is no Git repository, package manifest, lockfile, application source, or existing test suite.
- No generated spec-test manifest exists under `thoughts/tests/`.
- `thoughts/handoff/App.dc.html` is a visual interaction reference, not production code or a functional contract.
- The current contracts supersede prototype behavior involving activation, deletion, telemetry, remote discovery, AI generation, semantic graphs, and package lifecycle management.
- Local Node.js, pnpm, and Git are available, but implementation must pin supported engine versions in the repository rather than rely on the current machine.

## Requirements

### Product

- [ ] Run as a desktop application on macOS, Windows, and Linux.
- [ ] Discover Codex and user-configured Agent Skills-compatible roots.
- [ ] Obtain explicit approval before scanning a proposed root.
- [ ] Index valid and invalid skill directories without silently dropping parse failures.
- [ ] Show canonical path, scope, runtime, provenance, validity, precedence, and evidence state.
- [ ] Search, filter, group, and sort the inventory.
- [ ] Inspect `SKILL.md` and supporting resources without executing content.
- [ ] Edit skills only inside approved user-writable roots.
- [ ] Install from a local directory or local ZIP into an approved user-writable root.
- [ ] Update from the same verified local source when its content hash changes.
- [ ] Preview every write, persist a journal, create recovery data, verify the result, and support restart-safe undo.
- [ ] Observe harness state only when evidenced; never mutate activation or harness configuration.
- [ ] Never request privilege elevation or recommend weakening filesystem permissions.
- [ ] Publish official binaries only as release assets in the source repository.

### Quality and security

- [ ] Keep Node.js APIs out of the renderer.
- [ ] Use a narrow, typed, runtime-validated preload bridge.
- [ ] Use `contextIsolation`, renderer sandboxing, a restrictive CSP, navigation blocking, and Electron fuses.
- [ ] Reject traversal, unsafe archive paths, external symlink escapes, stale plans, and destination collisions.
- [ ] Preserve unknown frontmatter and user formatting during targeted edits.
- [ ] Support keyboard-only workflows, high contrast, reduced motion, resizable windows, and platform shortcuts.
- [ ] Exercise filesystem and operation fixtures natively on macOS, Windows, and Linux CI runners.

## Approach Analysis

### Option A: Modular pnpm workspace with filesystem-first core

**Description**: Use one Electron application plus internal packages for contracts, domain logic, adapters, scanning, storage, and operations. The main process owns privileged services; the renderer consumes only a typed preload API. SQLite implements repositories but never becomes the source of installed state.

**Pros**:

- Makes the trust boundary visible in the project structure.
- Keeps adapter and operation logic testable without launching Electron.
- Prevents UI concerns from leaking into filesystem behavior.
- Allows SQLite or a runtime adapter to be replaced behind stable interfaces.
- Supports native fixture tests across operating systems.

**Cons**:

- More initial configuration and package boundaries.
- Requires explicit workspace build ordering and lint boundary rules.
- Shared types must remain serialization-safe across IPC.

**Complexity**: Medium.

### Option B: Single Electron package organized by feature folders

**Description**: Keep main, preload, renderer, adapters, storage, and operations under one `src/` tree with TypeScript path aliases.

**Pros**:

- Fastest scaffold.
- Fewer package manifests and build configuration files.
- Straightforward local debugging.

**Cons**:

- Easier to import Node-only code into the renderer accidentally.
- Runtime adapters and operation engine become coupled to Electron earlier.
- Cross-platform fixture testing and future adapter extraction are harder.

**Complexity**: Low initially, medium-high as features accumulate.

### Option C: Tauri shell with a TypeScript renderer

**Description**: Use React/TypeScript for the interface and Rust commands for filesystem and persistence.

**Pros**:

- Smaller binary footprint.
- Strong native command boundary.

**Cons**:

- Violates the TypeScript-only application-code decision.
- Adds a second language, toolchain, and platform debugging surface.
- Slows the adapter and operation work that dominates this product.

**Complexity**: High for this team and constraint set.

### Recommendation

Choose **Option A**. Forge's risk is not the amount of UI code; it is safe cross-platform filesystem behavior. Separate packages make those boundaries explicit and testable while retaining TypeScript throughout the application code.

### Persistence decision

SQLite must sit behind a small repository interface. The implementation spike compares:

1. `node:sqlite` from Electron's embedded Node runtime: no external native addon, but its stability and exact Electron availability must be verified.
2. `better-sqlite3`: mature synchronous API, but requires Electron native-module rebuild and packaging validation on three platforms.

Select `node:sqlite` only if the pinned Electron runtime exposes the required API and packaged smoke tests pass on all three platforms. Otherwise use `better-sqlite3` in the main process. Do not add an ORM in the MVP; explicit SQL migrations keep the projection understandable and minimize dependencies.

### Initial installation-source decision

The MVP accepts only:

- A user-selected local directory.
- A user-selected local `.zip` archive.

Forge records the source locator, source tree hash or archive SHA-256, installed tree hash, and observation time. Update discovery re-reads that same local source. Arbitrary URLs, registries, Git cloning, and background downloads remain outside the MVP.

## Target Architecture

```text
apps/desktop
├── main             Electron lifecycle, windows, IPC registration
├── preload          narrow ForgeBridge exposed with contextBridge
└── renderer         React UI and transient view state

packages
├── contracts        serializable Zod IPC/domain schemas
├── domain           entities, evidence, status, pure resolution rules
├── adapter-api      runtime adapter interface and capability model
├── adapter-codex    Codex root discovery and verified semantics
├── adapter-folder   user-configured Agent Skills folder behavior
├── scanner          traversal, parsing, hashing, validation, watchers
├── storage          SQLite migrations and repositories
├── operations       plans, staging, journal, verification, recovery
└── test-fixtures    cross-platform skill trees and failure fixtures
```

### Runtime flow

```text
approved roots
  → adapter discovery
  → safe scanner / parser / validator
  → immutable observations
  → SQLite projection
  → typed IPC query
  → renderer inventory

install or update request
  → Zod IPC validation
  → persisted operation plan
  → preview and explicit confirmation
  → stage → snapshot → apply → rescan/verify → commit
  → persisted undo or recovery-required state
```

### Trust boundary

```ts
// packages/contracts/src/ipc.ts
export const forgeApi = {
  inventoryList: z.object({ scopeId: z.string().optional() }),
  operationPlan: z.discriminatedUnion("kind", [
    installRequestSchema,
    sourceUpdateRequestSchema,
    contentUpdateRequestSchema,
  ]),
  operationConfirm: z.object({ planId: z.string().uuid() }),
  operationUndo: z.object({ journalId: z.string().uuid() }),
} as const
```

The renderer never supplies arbitrary filesystem commands. Requests refer to approved root IDs, installation IDs, source-selection tokens created by a native dialog, and persisted plan IDs.

## Implementation Phases

## Phase 0: Close technical unknowns

### Task 0.1: Validate the Codex adapter contract

**Files**: `thoughts/ADAPTERS.md`, `thoughts/research/codex-adapter.md`, `packages/test-fixtures/codex/**`

Verify roots, project detection, precedence, observable runtime state, managed/read-only locations, and user-writable install targets using official documentation plus controlled local fixtures. Replace every Codex `Verify` entry with `supported`, `read-only`, `unsupported`, or `unknown` and evidence.

```ts
type VerifiedCapability = {
  state: "supported" | "read-only" | "unsupported" | "unknown"
  evidence: { kind: "documented" | "fixture"; reference: string }[]
}
```

No activation or configuration mutation is investigated as a Forge capability.

### Task 0.2: Prove the Electron, Vite, and SQLite packaging combination

**Files**: temporary spike outside production packages; results saved to `thoughts/research/storage-and-packaging-spike.md`

Build minimal packaged applications on each native CI platform that:

1. Start through Electron Forge with pinned Vite integration.
2. Open a local SQLite database through the candidate driver.
3. Apply one migration, write, close, reopen, and read.
4. Package without loading Node APIs in the renderer.
5. Confirm the database remains in `app.getPath("userData")`, never in the application bundle.

The spike output selects and records one SQLite driver. Spike code is discarded after the decision; the evidence document remains.

### Task 0.3: Freeze local source and archive rules

**Files**: `thoughts/OPERATIONS.md`, `thoughts/research/local-source-contract.md`, `packages/test-fixtures/imports/**`

Define directory and ZIP size limits, maximum files and nesting, symlink policy, ignored metadata files, hashing order, provenance fields, collision behavior, and rollback semantics. Undoing a successful install may remove only the exact unchanged tree created by that journal entry; this is operation rollback, not a general uninstall feature.

```ts
type LocalInstallSource =
  | { kind: "directory"; selectionToken: string; treeHash: string }
  | { kind: "zip"; selectionToken: string; archiveSha256: string }
```

## Phase 2: Domain, parsing, and persistence

### Task 2.1: Implement domain and evidence types

**Files**: `packages/domain/src/**`, `packages/contracts/src/domain/**`

Implement the entities and invariants from `DOMAIN.md`. Keep domain logic pure and filesystem-independent. Every optional claim uses `Evidenced<T>`; `unknown` never receives a fabricated value.

### Task 2.2: Implement canonical path and root authorization services

**Files**: `packages/scanner/src/paths/**`, platform fixtures

Canonicalize paths, resolve aliases according to policy, deduplicate roots, detect symlink/junction cycles, and prove containment before any read or write. Authorization uses approved root IDs, not renderer-provided path prefixes.

```ts
interface ApprovedRootPolicy {
  authorizeRead(rootId: string, candidate: string): Promise<CanonicalPath>
  authorizeWrite(rootId: string, candidate: string): Promise<CanonicalPath>
}
```

`authorizeWrite` fails for managed, system, denied, missing, or non-user-writable roots and never attempts elevation.

### Task 2.3: Implement skill parser, validator, and deterministic hashing

**Files**: `packages/scanner/src/parser/**`, `validation/**`, `hashing/**`

Parse frontmatter and raw body, preserve source text, enumerate resources, reject external references, and produce findings rather than dropping invalid skills. Hash normalized path names plus raw bytes in deterministic order without rewriting line endings.

### Task 2.4: Implement SQLite projection and repositories

**Files**: `packages/storage/src/**`

Create explicit migrations for settings, approved roots, projects, installations, snapshots, provenance, findings, operation plans, journal steps, and recovery records. Enable foreign keys and safe transaction settings. Rebuilding inventory tables from disk must not destroy journal or snapshot history.

```ts
interface ForgeStore {
  projections: ProjectionRepository
  snapshots: SnapshotRepository
  operations: OperationJournalRepository
  settings: SettingsRepository
}
```

## Phase 3: Adapters and observation pipeline

### Task 3.1: Implement the adapter API and admission test kit

**Files**: `packages/adapter-api/src/**`, `packages/adapter-api/test/**`

Turn `ADAPTERS.md` into TypeScript interfaces, capability declarations, and reusable contract tests. An adapter cannot advertise a mutating capability without producing a valid operation plan and passing postcondition fixtures.

### Task 3.2: Implement the generic folder adapter

**Files**: `packages/adapter-folder/src/**`, fixtures

Support explicitly configured Agent Skills-compatible roots. Parse and validate installations, derive scope from the approved root, and return `unsupported` for host precedence or runtime state not proven by the folder convention.

### Task 3.3: Implement the verified Codex adapter

**Files**: `packages/adapter-codex/src/**`, fixtures

Implement only the capabilities closed in Task 0.1. Managed plugin/cache roots remain read-only. Installation and update plans target only verified user-writable Codex roots.

### Task 3.4: Build scan coordination and watcher reconciliation

**Files**: `packages/scanner/src/coordinator/**`, `workers/**`, main service composition

Stream observations, parse failures, and progress without blocking the renderer or Electron event loop. Correlate self-generated watcher events with journal IDs, debounce external bursts, invalidate stale plans, and recover from missing roots.

## Phase 4: Read-only product vertical

### Task 4.1: Implement onboarding and approved-root management

**Files**: renderer onboarding feature, main root service, settings repository

First launch presents proposed roots with evidence and access labels. The user can include, exclude, and add roots through native directory selection. The first scan cannot begin until approval is persisted.

### Task 4.2: Build the responsive application shell and design tokens

**Files**: renderer app shell, tokens, base components, accessibility tests

Translate the handoff's visual character into responsive, semantic React components. Retain the dark material language and glass selection, but replace fixed macOS dimensions and controls with platform-aware window behavior. Use semantic buttons, tables/lists, dialogs, labels, and focus management.

### Task 4.3: Build inventory query and navigation

**Files**: renderer inventory feature, IPC query handlers, projection queries

Implement `Todas`/`Esta máquina`, true `Global`, and project scopes. Add search, evidence-aware filters, author/package grouping only when evidenced, deterministic sorting, selection, empty states, and keyboard navigation. Do not include activation toggles.

### Task 4.4: Build inspector, validation, and read-only source view

**Files**: renderer inspector feature, Markdown/source components

Show canonical path, runtime, scope, precedence explanation, provenance, independent status dimensions, findings, requirements, and files. Render Markdown with raw HTML disabled or sanitized. Unsupported and unknown values remain explicit.

## Phase 5: Safe install and update operations

### Task 5.1: Implement operation plans, journal, recovery, and undo

**Files**: `packages/operations/src/core/**`, storage journal repositories, recovery startup service

Implement the state machine from `OPERATIONS.md`. Every plan records preconditions, hashes, affected paths, backup strategy, postconditions, and undo. On startup, incomplete operations resolve to rolled back, committed, or recovery-required before new writes are accepted.

```ts
type OperationKind = "install" | "update-source" | "update-content"
type OperationState =
  | "planned"
  | "preconditions-checked"
  | "staged"
  | "snapshot-created"
  | "applying"
  | "verifying"
  | "committed"
  | "rolling-back"
  | "rolled-back"
  | "recovery-required"
```

### Task 5.2: Implement direct content update

**Files**: operation content-update executor, CodeMirror editor feature, diff preview

Edit writable skill files with external-change detection, raw-source preservation, snapshots, atomic sibling replacement, rescan verification, and restart-safe undo. Read-only installations expose no edit action.

### Task 5.3: Implement local directory and ZIP installation

**Files**: source-selection service, archive staging, install executor, install UI

Use native file/directory dialogs to mint opaque selection tokens. Enforce the Task 0.3 limits before preview. Validate the staged tree, show the complete destination diff, reject collisions by default, then copy atomically where possible. Do not execute or import any bundled code.

### Task 5.4: Implement local-source update discovery and apply

**Files**: update observation service, source-update executor, pending UI

For Forge-installed skills with reachable local provenance, hash the source on explicit refresh or watcher observation. Report `available`, `current`, `diverged`, or `unknown` using installed/base/local hashes. A diverged installation requires explicit conflict handling and is never silently overwritten.

### Task 5.5: Build operation preview, progress, history, and undo UI

**Files**: renderer operations feature, IPC event subscriptions

Display exact paths, scopes, warnings, conflicts, stage, cancellability, and recovery state. Toasts summarize committed results but history remains authoritative. Undo installation removes only the unchanged tree created by that journal entry; undo update restores its snapshot after checking for subsequent edits.

## Phase 6: Cross-platform hardening and repository releases

### Task 6.1: Complete native test and accessibility matrix

**Files**: unit/integration suites, `tests/e2e/**`, `.github/workflows/ci.yml`

Run lint, typecheck, unit, adapter contract, filesystem integration, Electron E2E, and packaging smoke tests on macOS, Windows, and Linux. Cover keyboard-only onboarding, inventory, inspector, editor, operation confirmation, and undo after restart.

### Task 6.2: Harden packaging and Electron configuration

**Files**: Forge config, fuses, CSP, protocol, makers

Package platform-native artifacts without auto-update code. Verify ASAR behavior, source maps, production DevTools policy, navigation denial, external-link allowlist, IPC sender validation, and fuse configuration. Document signing/notarization separately from the official-download channel.

### Task 6.3: Implement repository-only release workflow

**Files**: `.github/workflows/release.yml`, `README.md`, `SECURITY.md`

Build artifacts on native runners, attach them only to a tagged repository release, and publish SHA-256 checksums plus build metadata. Do not publish to stores, mirrors, package registries, or a standalone update endpoint. Keep release publishing manual until signing policy is decided.

### Task 6.4: Run beta acceptance and post-review

**Files**: acceptance evidence in `thoughts/reviews/**`, contract status updates

Exercise every success criterion in `PRODUCT.md`, resolve architecture or security findings, run `devtronic:post-review`, and update contract/plan status only after evidence is recorded.

## Risk Analysis

### Product and semantic risks

- [ ] Codex precedence or root rules may be undocumented or change. Keep unsupported behavior explicit and fixtures versioned.
- [ ] “Update” can be confused with harness reload or activation. Copy and status language must say content update only.
- [ ] Local source paths can disappear or change identity. Report `unknown` or require reselection; never guess a replacement source.
- [ ] Prototype screens contain removed features. Maintain a written prototype-to-MVP mapping before UI implementation.
- [ ] Package/author/version metadata may be missing. Preserve evidence states in every query and component.

### Filesystem edge cases

- [ ] Case-only collisions on Windows and default macOS filesystems.
- [ ] Symlink/junction cycles and links escaping approved roots.
- [ ] Locked files, antivirus interference, network/UNC paths, and removable drives.
- [ ] Source changes between preview and confirmation.
- [ ] Destination appears after planning.
- [ ] Process interruption at every journal state.
- [ ] Undo attempted after a third party changes installed content.
- [ ] ZIP traversal, absolute paths, decompression bombs, duplicate entries, and Unicode normalization.
- [ ] Very large trees or files exhausting memory; scanning and hashing must stream and enforce limits.

### Technical risks

- [ ] Forge's Vite integration can introduce packaging regressions. Pin exact versions and prove packaged smoke tests before feature work.
- [ ] SQLite driver compatibility differs from development Node. Test inside the pinned Electron runtime and packaged artifacts.
- [ ] Synchronous SQLite APIs can block Electron main. Keep transactions short, benchmark projections, and move heavy work behind a worker boundary if thresholds fail.
- [ ] Watchers behave differently across platforms. Watchers trigger reconciliation only; they never directly mutate authoritative state.
- [ ] Renderer IPC DTOs may drift from domain types. Generate/infer types from the same Zod schemas and contract-test both ends.
- [ ] Signing and notarization may not be ready for the first build. Keep packaging/release verifiable independently and document OS warnings honestly.

### Security risks

- [ ] Imported Markdown or HTML can become script execution in the renderer. Disable raw HTML or sanitize it and keep CSP restrictive.
- [ ] IPC path injection can escape approved roots. Use opaque IDs/tokens and re-authorize in main immediately before apply.
- [ ] Archives can consume unbounded resources. Apply compressed and expanded limits before extraction completes.
- [ ] Dependency compromise affects a privileged desktop app. Minimize dependencies, pin lockfile, audit production graph, and automate review alerts without automatic merges.
- [ ] Recovery data may expose private skill content. Store under user data with user-only permissions where supported and document retention.

## Testing Strategy

### Unit tests

- Evidence propagation and unknown-state behavior.
- Canonical identity, scope distinction, precedence resolution, and status composition.
- Frontmatter parsing without source normalization.
- Deterministic tree hashing and resource reference validation.
- Operation state-machine transitions and invalid transition rejection.
- ZIP entry validation and limit accounting.
- Zod IPC input/output schemas.

### Adapter contract tests

- Minimal valid and invalid skills.
- Missing frontmatter and unknown metadata.
- Duplicate names, scope collision, and precedence when supported.
- Read-only managed roots.
- Unsupported runtime state and missing provenance.
- Unicode, spaces, mixed case, CRLF, symlinks, and junctions.

### Integration tests

- Scan approved temporary roots and rebuild SQLite projections.
- Install directory and ZIP fixtures into a temporary writable root.
- Reject writes to non-approved and read-only roots without elevation.
- Detect stale plan, source change, destination collision, and external edit.
- Interrupt each operation stage and recover after a simulated restart.
- Undo install/update only when postconditions still match.
- Correlate watcher events with the active journal operation.

### Electron E2E tests

- First launch → approve roots → scan → inventory → inspector.
- Search/filter/group/sort and keyboard navigation.
- Open a read-only installation and confirm editing is unavailable.
- Edit writable content → preview → confirm → undo after relaunch.
- Install local fixture → preview → confirm → undo after relaunch.
- Detect a changed local source → preview update → confirm.
- Attempt stale/conflicting operation and reach a safe recovery message.
- Confirm activation/deactivation controls never appear.

### Packaging tests

- `pnpm make` succeeds on each native runner.
- Packaged app launches and creates/reopens its SQLite store.
- Renderer has no Node globals and cannot call undeclared IPC channels.
- Release workflow emits repository assets and SHA-256 checksums only.

### Manual verification

1. Run the packaged artifact on each OS, not only development mode.
2. Add a real user-owned root and inspect several valid and invalid skills.
